# Gandalf Slack bot

Gandalf is wise, calm, warm, and direct, with a subtle wizardly voice. He uses Slack-native Markdown for readable answers and brief progress updates for high-reasoning requests; progress describes work being done rather than private reasoning. He answers questions, reads the current Gantt chart, and adds one or more custom tasks to the same backend as the chart. Gandalf can schedule up to 25 items in one request; if any item needs details, it asks before creating the batch. Send Gandalf a direct message, or mention Gandalf in a channel or in a thread, for example:

> @Gandalf Schedule the Acme export fix from December 1 to December 3.

In a thread, Gandalf uses the earlier thread messages to infer the customer and task. If a required detail is missing or ambiguous, it asks a question. When channel replies are enabled, Gandalf can also respond without an @mention when named or when a message seems relevant; it considers human messages in channels where the bot is present, ignores bot messages, and does not schedule tasks from messages not addressed to it. In a direct message, reply normally without a mention. Gandalf keeps the last 100 Gandalf exchanges separately for each channel or direct message, and also reads up to 20 recent direct messages or the current Slack thread for context. Exchanges are stored on the same persistent volume as the chart; earlier exchanges are not backfilled. A single specified date is used as both the start and end date. Relative dates use `GANDALF_TIMEZONE` (default `America/New_York`). The chart refreshes its data every 30 seconds.

## Set up

1. Deploy the updated `server` to the **same Railway service** used by the chart, and deploy the updated `client` to Cloudflare Pages. The current production client points to `https://linear-gantt-production.up.railway.app`. Confirm this is still the correct service before proceeding.
2. Create a Slack app named Gandalf in the intended workspace. Add a bot user and the bot token scopes `app_mentions:read`, `chat:write`, `im:history`, `channels:history`, and, if using private channels, `groups:history`. Enable Event Subscriptions and subscribe to the bot events `app_mention`, `message.im`, `message.channels`, and `message.groups`. Enable the Messages tab and allow users to send messages in App Home. Install the app to the workspace and invite Gandalf to the channels where it should be used.
3. Set Railway environment variables `OPENAI_API_KEY`, `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, and `SLACK_TEAM_ID`. Get the signing secret from the app's Basic Information and bot token from OAuth & Permissions; use the workspace's team ID for `SLACK_TEAM_ID`. Set `OPENAI_MODEL` and `OPENAI_REASONING_EFFORT` to a compatible reasoning model and effort (production uses `gpt-5.4` and `high`). Set `GANDALF_TIMEZONE` if its default is unsuitable. Gandalf classifies each prompt using `OPENAI_ROUTER_MODEL` (default `gpt-5.4-mini`), with recent conversation context. Low-complexity requests use `OPENAI_LOW_MODEL` (default `gpt-5.4-mini`) and `OPENAI_LOW_REASONING_EFFORT` (default `low`); high-complexity requests use `OPENAI_HIGH_MODEL` or `OPENAI_MODEL` and `OPENAI_HIGH_REASONING_EFFORT` or `OPENAI_REASONING_EFFORT` (production defaults: `gpt-5.4`, `high`). When any search is needed, Gandalf upgrades to high reasoning for search planning and synthesis, with up to twenty combined search or browser actions per request. If classification fails, Gandalf uses the high path. Configure compatible models and effort values. Do not commit credentials. Rotate any key shared in chat before using it.
4. Set the Slack Events Request URL to `https://linear-gantt-production.up.railway.app/api/slack/events` (or the actual backend URL). Slack validates the endpoint using a signed challenge, so deploy and set the signing secret first. Save the subscription and reinstall the app if Slack requests it.
5. Test in a channel with a task, customer and date, then test a thread with missing details. The bot posts its result in the thread and the chart should show the task after refresh.

Slack's thread access and rate limits depend on app distribution and token type. If `conversations.replies` fails for channel threads, provide `SLACK_HISTORY_TOKEN` as an authorized user token with `channels:history` and/or `groups:history`, and ensure that user can access the channels. Slack conversation text and current chart data are sent to OpenAI to answer requests; only use the bot in channels where that is appropriate. Only the thread up to the triggering message is read; a top-level channel message uses its own text, not preceding channel history. For non-mention channel replies, set `GANDALF_CHANNEL_REPLIES=true` and `SLACK_BOT_USER_ID` to the bot user ID; Slack must deliver the `message.channels` and `message.groups` events. Channel messages considered for relevance may be sent to OpenAI.

The existing storage is a local JSON file. Ensure the Railway service runs **one instance** and its existing data directory is on persistent storage, with backups, before relying on the chart. `GANTT_DATA_DIR` can select a mounted directory, but moving an existing chart requires migrating its `tickets.json` first. The write lock and Slack retry suppression are per process; asynchronous events can be lost if the process stops immediately after acknowledging them. A durable queue and shared transactional database are needed for stronger delivery guarantees or multiple instances.

## Read-only search

When `GANDALF_CHANNEL_SEARCH=true`, the configured owner’s Slack and Granola search can be used in channels and other users’ DMs, and results may be shared in those conversations. Pylon search remains restricted to the owner’s direct chat. Set `GANDALF_SEARCH_OWNER` to the owner's Slack user ID. Set `SLACK_SEARCH_TOKEN` to that person's Slack user OAuth token with `search:read`; the bot verifies the token identity and workspace before each Slack search. Set `GRANOLA_API_KEY` to the same person's authorized Granola API key. Set `PYLON_API_TOKEN` to an authorized read-only Pylon token; Pylon access is also limited to the owner's DM. These credentials are separate from the connections used by ChatGPT and must be configured on Railway.

Each Slack search is bounded to 10 matching messages and includes source links; it does not automatically retrieve surrounding threads. Granola searches scan at most 300 accessible note records and return up to 10 matches; the API path used here does not search full transcripts and reports when the scan is incomplete. Search results, conversation text and chart data may be sent to OpenAI. The owner-authorized Slack user token is validated against the owner and workspace before search; never reveal the token.

Pylon keyword search checks issue titles and initial bodies and returns at most 10 issues; it does not search complete conversations. An exact issue number retrieves issue details and up to the first 50 messages, including internal notes, and reports when more messages remain. Gandalf does not update Pylon or send Pylon replies.

For read-only code inspection, Gandalf searches the public `superdoc/docx-editor` GitHub repository without a token, restricted to the configured owner's DM. Each inspection resolves the latest `main` commit and reads a public source archive or file at that immutable revision; it does not access private Orbit or local uncommitted changes, execute code, or create a working checkout. Search is bounded to 10,000 text files and 8 matching files; file and archive size limits apply. GitHub's unauthenticated API has rate limits. Code sent in context is processed by the configured OpenAI API.

The codebase contains an unconnected alert-verification helper for future `#int-demo-gallery` CI monitoring. It validates the exact `superdoc/demos` run and attempt against GitHub before any action. No autonomous CI fixing, channel monitoring, posting, pushing, or merging is enabled by this helper.

## Browser

The separate `browser-service` runs Chromium through Playwright and lets Gandalf open and reload public HTTP(S) pages, inspect text and screenshots, click, fill fields, press keys, and scroll. Sessions are isolated by Slack conversation and user and expire after 15 minutes of inactivity. It is deployed without the chart volume or application credentials; `GANDALF_BROWSER_URL` and `GANDALF_BROWSER_SECRET` connect the chart backend to it over Railway's private network. The browser service must receive the same secret. Public-address-only proxying blocks local and private network access for HTTP(S) and WebSockets; downloads are disabled. For each opened page Gandalf plans a task-specific test script, makes several passes when feasible, reloads between passes only after finishing the current exploratory session when a fresh page state helps, and reports observations and untested steps. Browser output is bounded, and page content is untrusted. Browser interactions may change data on the visited website; the browser does not have access to the user's existing logged-in browser session.

When asked to test a demo app or example, Gandalf interacts with it and applies the Demo Impact Scorecard: Relevance, Clarity, and Differentiation, each scored from 1 to 5 with evidence. It recommends whether to keep, improve, merge, or retire the demo, without taking those actions. Insufficient evidence is marked not assessed; agents, bots, galleries, and delivery infrastructure are outside the scorecard. The rubric is defined in `server/src/services/demo-scorecard.ts`.

## Proactive guidance

Set `GANDALF_PROACTIVE_ENABLED=true` and `GANDALF_PROACTIVE_DM_CHANNEL` to the owner's verified Gandalf DM. The watcher checks the chart, a bounded set of recent Granola notes, and one chart customer in Slack every 10 seconds; it rotates through up to 12 customers. It checks the first 25 active issues assigned to the Linear token owner and rotates through up to 12 chart-linked Pylon issues every two minutes when configured. Search results and note coverage are bounded, Pylon requires its token, and source errors and timestamps are included with the evidence.

Gandalf compares source snapshots with persisted baselines and uses the high-reasoning model to assess meaningful changes at most every five minutes. He sends one combined update only when there is a meaningful new development, at most once per `GANDALF_PROACTIVE_MIN_MESSAGE_MINUTES` (default and production: 60); he does not send routine check-ins when nothing new is found. Newly observed sources are baselined before their changes can trigger updates. Proactive messages are suppressed from 10 p.m. until 6 a.m. in `GANDALF_TIMEZONE` (default America/New_York), including when a response crosses into quiet hours. Messages are recorded in the owner's DM conversation history. Source baselines, snapshot fingerprints, sent-message hashes, and recent proactive messages persist on the same volume in `gandalf-proactive.json`. To disable proactive checks and messages, set `GANDALF_PROACTIVE_ENABLED=false` and redeploy; ordinary Gandalf chat is unaffected.

### Demo reviewers

For browser explorations, Gandalf can consult Bilbo, a separate opinionated model reviewer who sees bounded browser observations and may suggest follow-up tests but does not browse. Thorin independently probes the page in a separate browser session, with up to eight actions after opening, to challenge the happy path and look for failure modes. Both treat page contents as untrusted. Thorin avoids unrequested irreversible actions and reloads only after finishing the current exploratory session. Gandalf synthesizes their findings, briefly attributes their takes and his agreement or disagreement, and remains responsible for the final score. Failed or incomplete reviews must not be represented as successful tests.

For other questions Gandalf may consult Bilbo and Thorin as independent, tool-free advisers when a second perspective would help. They receive only the current conversation and already-authorized evidence, and cannot independently search or browse in this mode. Gandalf decides which opinions, if any, to use or mention.

### Message cleanup

Gandalf can edit or delete his own messages in the current thread, or within the recent bounded conversation history when there is no thread, when asked or when a message is redundant. The server verifies ownership against Slack's authenticated bot identity; it never changes another user's or bot's messages and does not delete a thread parent. Automatic cleanup preserves his latest message. A request to keep the latest message is also enforced. Cleanup is limited to 25 messages per request; Slack errors or unavailable history can prevent it. Progress updates are replaced by the final answer when possible, keeping the thread shorter.
