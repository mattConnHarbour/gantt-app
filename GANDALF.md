# Gandalf Slack bot

Gandalf answers questions, reads the current Gantt chart, and adds one or more custom tasks to the same backend as the chart. Gandalf can schedule up to 25 items in one request; if any item needs details, it asks before creating the batch. Send Gandalf a direct message, or mention Gandalf in a channel or in a thread, for example:

> @Gandalf Schedule the Acme export fix from December 1 to December 3.

In a thread, Gandalf uses the earlier thread messages to infer the customer and task. If a required detail is missing or ambiguous, it asks a question. For channel threads, reply in the same thread and @mention Gandalf again. In a direct message, reply normally without a mention. Gandalf keeps the last 100 Gandalf exchanges separately for each channel or direct message, and also reads up to 20 recent direct messages or the current Slack thread for context. Exchanges are stored on the same persistent volume as the chart; earlier exchanges are not backfilled. A single specified date is used as both the start and end date. Relative dates use `GANDALF_TIMEZONE` (default `America/New_York`). The chart refreshes its data every 30 seconds.

## Set up

1. Deploy the updated `server` to the **same Railway service** used by the chart, and deploy the updated `client` to Cloudflare Pages. The current production client points to `https://linear-gantt-production.up.railway.app`. Confirm this is still the correct service before proceeding.
2. Create a Slack app named Gandalf in the intended workspace. Add a bot user and the bot token scopes `app_mentions:read`, `chat:write`, `im:history`, `channels:history`, and, if using private channels, `groups:history`. Enable Event Subscriptions and subscribe to the bot events `app_mention` and `message.im`. Enable the Messages tab and allow users to send messages in App Home. Install the app to the workspace and invite Gandalf to the channels where it should be used.
3. Set Railway environment variables `OPENAI_API_KEY`, `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN`, and `SLACK_TEAM_ID`. Get the signing secret from the app's Basic Information and bot token from OAuth & Permissions; use the workspace's team ID for `SLACK_TEAM_ID`. Set `OPENAI_MODEL` and `OPENAI_REASONING_EFFORT` to a compatible reasoning model and effort (production uses `gpt-5.4` and `high`). Set `GANDALF_TIMEZONE` if its default is unsuitable. The server omits reasoning effort when it is not configured, for compatibility with models that do not support it. Do not commit credentials. Rotate any key shared in chat before using it.
4. Set the Slack Events Request URL to `https://linear-gantt-production.up.railway.app/api/slack/events` (or the actual backend URL). Slack validates the endpoint using a signed challenge, so deploy and set the signing secret first. Save the subscription and reinstall the app if Slack requests it.
5. Test in a channel with a task, customer and date, then test a thread with missing details. The bot posts its result in the thread and the chart should show the task after refresh.

Slack's thread access and rate limits depend on app distribution and token type. If `conversations.replies` fails for channel threads, provide `SLACK_HISTORY_TOKEN` as an authorized user token with `channels:history` and/or `groups:history`, and ensure that user can access the channels. Slack conversation text and current chart data are sent to OpenAI to answer requests; only use the bot in channels where that is appropriate. Only the thread up to the mention is read; a top-level mention uses its own message, not preceding channel history.

The existing storage is a local JSON file. Ensure the Railway service runs **one instance** and its existing data directory is on persistent storage, with backups, before relying on the chart. `GANTT_DATA_DIR` can select a mounted directory, but moving an existing chart requires migrating its `tickets.json` first. The write lock and Slack retry suppression are per process; asynchronous events can be lost if the process stops immediately after acknowledging them. A durable queue and shared transactional database are needed for stronger delivery guarantees or multiple instances.

## Read-only search

Personal Slack, Granola and Pylon searches are restricted to the configured owner's direct chat with Gandalf, not channels or other users. Set `GANDALF_SEARCH_OWNER` to the owner's Slack user ID. Set `SLACK_SEARCH_TOKEN` to that person's Slack user OAuth token with `search:read`; the bot verifies the token identity and workspace before each Slack search. Set `GRANOLA_API_KEY` to the same person's authorized Granola API key. Set `PYLON_API_TOKEN` to an authorized read-only Pylon token; Pylon access is also limited to the owner's DM. These credentials are separate from the connections used by ChatGPT and must be configured on Railway.

Slack results are bounded to 10 messages and include source links. Granola searches scan at most 300 accessible note records and return up to 10 matches; the API path used here does not search full transcripts and reports when the scan is incomplete. Search results, conversation text and chart data may be sent to OpenAI. Do not enable a shared search credential in channels or for other users.

Pylon keyword search checks issue titles and initial bodies and returns at most 10 issues; it does not search complete conversations. An exact issue number retrieves issue details and up to the first 50 messages, including internal notes, and reports when more messages remain. Gandalf does not update Pylon or send Pylon replies.
